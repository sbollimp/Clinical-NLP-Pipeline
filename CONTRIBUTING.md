# Contributing

Thanks for taking a look. This document covers how to get set up, the conventions the codebase
follows, and how to add each kind of thing.

---

## Setup

```bash
git clone <this-repo> && cd clinical-doc-nlp-pipeline
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
pip install pytest            # for the test suite

make run                      # regenerates every artefact in outputs/ (~35 s)
make test                     # 57 tests, a few seconds
```

No editable install is needed — `PYTHONPATH=src` (set for you by the Makefile and by
`pyproject.toml`'s pytest config) is enough. `pip install -e .` also works and gives you the
`clinical-nlp` console script.

---

## Non-negotiables

Three invariants hold the pipeline together. Breaking any of them breaks things far away from your
change, so tests guard all three.

**1. Offsets are sacred.** No stage may change note text in a way that shifts character positions.
Normalisation and de-identification are both length-preserving on purpose. Every `Span` must satisfy
`note.text[span.start:span.end] == span.text`. If a transformation would change length, it belongs in
concept normalisation (which produces a canonical *name*, not new text), not in preprocessing.

**2. Every prediction carries an explanation.** If you add a model, a rule, or a label, it ships with
whatever evidence produced it in the `explanation` dict. The rest of the codebase does not inspect the
internals of that dict, so you are free to put a new method's payload in it — but it must not be
empty.

**3. Nothing resembling real patient data enters this repository.** Not in tests, not in fixtures, not
in docstrings. `.gitignore` has guards; please do not work around them.

## Conventions

- **Line length 100.** `ruff` config is in `pyproject.toml` (`make lint`).
- **Type hints on public functions.** `from __future__ import annotations` at the top of every module.
- **Module docstrings explain *why*, not *what*.** The code says what it does. The docstring should
  say why it is done that way, and what the alternative would have cost. This is the single most
  useful convention in the codebase — please keep it up.
- **No new runtime dependencies** without a strong reason. Running with only scikit-learn, NumPy,
  SciPy, joblib and PyYAML is a feature of this project, not an accident.
- **Configuration goes in `configs/default.yaml`** and its dataclass in `config.py`. No magic numbers
  buried in functions.
- **British/American spelling:** the codebase uses `-ise` in prose and `-ize` in nothing that matters.
  Do not spend time on this.

## Adding things

### A new entity type

1. Add it to `ENTITY_TYPES` in `data/schema.py`.
2. Give the generator a way to write it (`data/generate.py`) so there is gold data to train on.
3. Add lexicon entries (`data/lexicons.py`) or a regex rule (`ner/rules.py`), whichever fits — a
   closed vocabulary wants the gazetteer, a generative pattern wants a rule.
4. Add a colour to `ENTITY_COLORS` / `ENTITY_BG` in `explain/report.py`.
5. Decide where it lands in `structure/assembler.py`.
6. Retrain: `make run`. The tagger picks it up automatically.

### A new regex rule

Add a `Rule` to `RULES` in `ner/rules.py` with a unique `id` and a human-readable `description`. Both
appear in the explanation payload, so write the description for a reviewer, not for yourself. Add a
`test_rules_extract_generative_entities` case, and — importantly — a negative case, like the existing
`test_lab_concentration_units_are_not_read_as_doses`.

### A new assertion cue

Add it to the relevant list in `data/lexicons.py`. Scoping logic lives separately in `ner/context.py`,
so a new cue needs no code change. Add a case to the `test_assertion_scoping` parametrisation, and
check it does not fire inside longer words (terminators are word-bounded for exactly this reason).

### A new document label

Add a `SingleLabelClassifier` or `MultiLabelClassifier` to `DocumentClassifierBundle` in
`classify/model.py`, wire it into `fit`/`predict`, add gold labels to the generator, and add a metrics
block in `cli.step_evaluate` plus a section in `metrics.format_markdown`.

### A different tagger backend

Implement `fit(docs)` and `predict_document(doc) -> List[Span]` in `ner/tagger.py`. `HybridNER` merges
whatever it is given. The only other contract is the `explanation` dict on each returned span — for a
transformer, put LIME or SHAP output there instead of exact weights, and say so in the `method` key.

## Tests

The suite protects **contracts**, not accuracy. Headline numbers live in `outputs/metrics.md` and are
regenerated by `make run`; the one accuracy assertion in the suite
(`test_pipeline_beats_a_sane_accuracy_floor`) is a loose regression guard, not a benchmark, and should
stay loose.

| File | Covers |
| --- | --- |
| `test_preprocess.py` | offset reconstruction, clinical tokenisation, section tiling and aliases |
| `test_ner_components.py` | BIO round-tripping and repair, rule precision, gazetteer longest-match, assertion scoping |
| `test_generator.py` | gold-annotation invariants, determinism, split disjointness, JSON round-trip |
| `test_pipeline.py` | end-to-end record shape, assertion-driven exclusion, attribute attachment, save/load |
| `test_evaluate_and_report.py` | metric arithmetic against hand-computed values, de-id length preservation, HTML escaping |

Run a subset with `pytest tests/test_ner_components.py -q`.

When you add a metric, add a test that checks it against a hand-computed value on a two-row example.
Metric bugs are silent and expensive.

## Pull requests

- One concern per PR.
- If you changed anything that affects the numbers, run `make run` and commit the regenerated
  `outputs/` in the same PR, so the committed artefacts always match the code.
- Update `docs/` when you change behaviour. The model card in particular should never describe a
  version of the pipeline that no longer exists.
- If you found a shortcut, a leak, or a failure mode — write it into `docs/model_card.md §5`. That
  section is more valuable than another point of F1.
